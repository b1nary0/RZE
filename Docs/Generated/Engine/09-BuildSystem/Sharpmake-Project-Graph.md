# Sharpmake Project Graph

RZE's projects are generated by [Sharpmake](https://github.com/ubisoft/Sharpmake), a C#-based build config generator
(conceptually similar to CMake or Premake), from one description for both platforms: Visual Studio solutions on
Windows, GNU Makefiles on Linux. Nothing generated is committed; only the `.sharpmake.cs` files are. This page details
the Sharpmake definitions; for the high-level dependency picture see
[Module-Dependency-Graph.md](../02-Architecture/Module-Dependency-Graph.md).

## Generation flow

```
Windows: RZE\GenerateSolutions.bat
  -> "../Tools/Sharpmake/Sharpmake.Application.exe" "/sources('RZE.sharpmake.cs')"
  -> RZE.sln, and a .vcxproj per project in its _project\ folder

Linux:   RZE/GenerateSolutions.sh
  -> dotnet ../Tools/Sharpmake/Sharpmake.Application.dll "/sources('RZE.sharpmake.cs')"
  -> RZE.make, and a <Project>_Linux.make per project in its _project/ folder
```

The same bundled Sharpmake 1.9.1 (the release's Windows build) runs on both: it targets .NET 8 and rolls forward
onto newer runtimes. Run the generator again after adding or removing a source file. On Linux, build the whole
solution with `make -f RZE.make config=debug` (or `release`, `retail`), or one project by naming it.

`RZE.sharpmake.cs` is the solution root. It includes the shared files and every project's file, and adds each project
to the solution: `Engine`, `Rendering`, `Utils`, `SourceAssetBurner`, `Externals`, `EditorLib`, `Editor`, `Game`,
`EditorHarness` and `UnitTests` on both platforms; `SharpmakeProjectBase` (Visual Studio only) on Windows; and
`OptickCore` on Linux, where Optick is built from its source (below). `Main.SharpmakeMain` pins the Windows SDK and
DevEnv (`vs2026`, which writes the v145 toolset, and Kits Root `10.0.26100.0`) and calls `arguments.Generate<RZE>()`.

## Shared build config

- **`Make/Sharpmake/CommonTarget.sharpmake.cs`**: `CommonTarget : ITarget`, with `Optimization` (Debug, Release,
  Retail) and the target for the machine generating: `win64` with `DevEnv.vs2026`, or `linux` with `DevEnv.make`.
  Any other host throws. `SubPlatformType` is only `x64`, and `Mode` only `Game`: the Editor and Game are separate
  executable projects, not a target axis.
- **`Make/Sharpmake/BaseProject.sharpmake.cs`**: the abstract `BaseProject : Project` every native project derives
  from.
  - **All platforms:** project files in the project's `_project/` folder as `[project.Name]_[target.Platform]`,
    binaries in `_build/<config>/` (lowercase, so the paths are the same on Linux's case-sensitive file system),
    include paths for the project's own `Src` and `ThirdParty/Include`.
  - **`ConfigureWin64`:** C++17, RTTI, Unicode, exceptions, warning level 3 as errors (4267 off), `NOMINMAX`, and
    `RZE_GFX_DX11`.
  - **`ConfigureLinux`:** clang (`clang++`), C++17, RTTI, exceptions, `-Wall -Werror`, symbols in every configuration,
    `-O0`/`-O2`/`-O3 -mavx2` for Debug/Release/Retail, `-pthread`, `RZE_GFX_OPENGL`, and LLD as the linker
    (`-fuse-ld=lld`). LLD finds symbols in static libraries in any order, as MSVC's linker does; GNU ld wouldn't,
    since the generator sorts libraries by name. Executables have no extension. `ThirdParty/Include` is a system
    include path (`-isystem`, passed as an option because the Makefile generator ignores `IncludeSystemPaths`), so
    warnings in vendored headers don't fail the build.
  - **Folder tokens.** A folder named `Windows` or `DX11` anywhere under a project's `Src` is compiled only on
    Windows; one named `Linux` or `OpenGL`, only on Linux. Per-platform code therefore needs no `#if`: e.g.
    `Utils/Platform/Windows/ShellWindows.cpp` and `Linux/ShellLinux.cpp` both implement `Shell.h`, and the build
    picks one. See [Platforms-And-Graphics-APIs.md](../06-Platform-And-Infrastructure/Platforms-And-Graphics-APIs.md).
  - `UsePrecompiledHeader(conf, target, name)` gives a project a precompiled header, `<name>.h` built by
    `<name>.cpp` in its `Src` ([below](#precompiled-headers)).
  - `ConfigureAsWindowedApp(conf)` builds a Windows exe as a windowed app (`SubSystem.Windows`, with
    `/ENTRY:mainCRTStartup` so the entry point is still `main`); the Editor and the Game use it, so no console window
    opens and takes focus from theirs ([Debug-Services-And-Logging.md](../06-Platform-And-Infrastructure/Debug-Services-And-Logging.md#the-console)).
    Elsewhere it does nothing.
- **`Make/Sharpmake/Sharpmake.sharpmake.cs`**: `SharpmakeProjectBase : CSharpProject`, the C# project wrapping
  Sharpmake itself inside the Visual Studio solution (in a "Tools" folder), referencing `Tools/Sharpmake/Sharpmake.dll`
  and `Sharpmake.Generators.dll` directly, so the solution can be edited and regenerated from inside Visual Studio.

## Per-project Sharpmake files

| Project | File | Output | `AddPublicDependency<T>` | Linked libraries: Windows / Linux |
|---|---|---|---|---|
| Utils | `Utils/Utils.sharpmake.cs` | static lib | *(none)* | — |
| Externals | `Externals/Externals.sharpmake.cs` | static lib | *(none)* | `SDL3` / `libSDL3.so`. ImGui's DX11 or GL3 backend is left out per platform. On Linux it compiles with `-w` (all of it is vendored: ImGui and its add-ons, glad, SPIRV-Cross) and adds glad's include path |
| OptickCore | `ThirdParty/OptickCore.sharpmake.cs` | static lib, Linux only | *(none)* | — ; built from `ThirdParty/Include/Optick` with `-w` and `OPTICK_ENABLE_GPU=0` |
| Modules/Rendering | `Modules/Rendering/Rendering.sharpmake.cs` | static lib | Externals, Utils (+ OptickCore on Linux) | `d3d9`, `d3d11`, `d3d12`, `dxgi`, `d3dcompiler`, `DirectXTK`, `OptickCore` / `libshaderc_shared.so` |
| Engine | `Engine/Engine.sharpmake.cs` | static lib | Utils, Externals, Rendering (+ OptickCore on Linux) | `OptickCore`, `dwmapi`, `comctl32`; copies `ThirdParty/Dll/x64/*.dll` beside the executables after building / — |
| SourceAssetBurner | `SourceAssetBurner/SourceAssetBurner.sharpmake.cs` | exe | **Engine only** | `assimp-vc141-mt` / `libassimp.so` |
| EditorLib | `Editor/Editor.sharpmake.cs` | static lib | **Engine only** | — (everything in `Editor/Src` except `EditorMain.cpp`; its own intermediate folder, since it shares `Editor/_project` with Editor) |
| Editor | `Editor/Editor.sharpmake.cs` | windowed exe | **EditorLib**, through `EditorLib.LinkWhole` | the whole of `EditorLib` (`/WHOLEARCHIVE` / `--whole-archive`), so self-registering panels aren't dropped; compiles only `EditorMain.cpp`, plus `Resources/Editor.rc` (the icon) on Windows |
| EditorHarness | `EditorHarness/EditorHarness.sharpmake.cs` | console exe | **EditorLib**, through `EditorLib.LinkWhole` | the Editor with a harness for automation drivers ([EditorHarness-And-Drivers](../07-Editor/EditorHarness-And-Drivers.md)) |
| Game | `Game/Game.sharpmake.cs` | windowed exe | **Engine only** | — ; `Resources/Game.rc` (the icon) on Windows |
| UnitTests | `UnitTests/UnitTests.sharpmake.cs` | exe | **EditorLib only** | — (doctest is header-only) |

`EditorLib.LinkWhole(conf, target)` is the one place that knows how to link the whole of EditorLib into an executable
(`/WHOLEARCHIVE:EditorLib.lib` on Windows, `-Wl,--whole-archive -l:libEditorLib.a -Wl,--no-whole-archive` on Linux).
The Editor and EditorHarness both call it.

`Game` and `SourceAssetBurner` declare a single explicit dependency, `Engine` (`Editor`, `EditorHarness` and
`UnitTests` declare `EditorLib`, which declares `Engine`), rather than also separately declaring `Utils` (and, for
`Game`, `Rendering`). That's enough: `Engine` itself has `AddPublicDependency<Utils>`/`<Externals>`/`<Rendering>`,
and Sharpmake's `AddPublicDependency` passes a project's public include and library paths on to everything that
depends on it.

Worth knowing if you audit this yourself:

- This table reflects the files as of the last check. If the build config keeps changing, re-verify against the
  `.sharpmake.cs` files rather than trusting it indefinitely.
- `Editor`, `EditorHarness` and `SourceAssetBurner` also have a raw
  `conf.IncludePaths.Add(Path.Combine(Globals.RootDir, "Utils"))` line pointing at the `Utils` project root (not
  `Utils/Src`). Given the transitive path already resolves, it looks vestigial.

## Precompiled headers

| Project | PCH (in its `Src`) | Holds |
|---|---|---|
| Utils | `UtilsPCH.h` | std containers and utilities, Utils core, the Utils math headers (and so GLM) |
| Engine | `EnginePCH.h` | `UtilsPCH.h`, then a few std headers, Optick, `RZE.h`, `EngineApp.h`, ImGui |
| EditorLib | `EditorLibPCH.h` (in `Editor/Src`) | `UtilsPCH.h` |
| UnitTests | `UnitTestsPCH.h` | `UtilsPCH.h` |
| EditorHarness | `EditorHarnessPCH.h` | `UtilsPCH.h` |

The Editor, Game and SourceAssetBurner executables, Rendering, Externals and OptickCore have none. Each PCH is built by
the `.cpp` of the same name. No source file includes it. Every file in the project gets the PCH first anyway:

- **Windows:** `UsePrecompiledHeader` adds the header to `ForcedIncludes`, so MSVC builds with `/FI` and `/Yu`, and
  the PCH's own `.cpp` with `/Yc`.
- **Linux:** the Makefile generator copies the header into the `obj` folder, builds a `.gch` beside the copy, and
  compiles every file with `-include` of that copy, which clang turns into `-include-pch`. Nothing more is forced
  there: another `-include` would look the header up by name through the include paths instead.

A file written on Linux therefore can't build there and then fail on MSVC for lacking the include (C1010).

**Each PCH is named after its project.** Both used to be `StdAfx.h`, and on Linux, Engine's `#include <StdAfx.h>`
found Utils' header first, as `Utils/Src` comes before Engine's own `Src` in its include paths. Every Engine file then
parsed Utils' PCH, GLM and all, as text after loading Engine's: about 0.8 s per file, nearly 40% of Engine's compile
time. MSVC's `/Yu` uses the PCH for everything up to that include without looking the header up, so Windows shouldn't
have had the problem. A `.cpp` in a project without a PCH got another project's header the same way.

An old Linux build folder needs a `make clean` once after the rename: its dependency files still name `StdAfx.h`.

**The PCHs are layered.** `UtilsPCH.h` holds what every project shares, is costly to parse and seldom changes: std
containers and utilities, Utils core (`Debug`, `File`, `Filepath`, `PrimitiveDefs`) and the Utils math headers, which
bring GLM. `EnginePCH.h` includes it first, then adds a few std headers and Engine's own (`RZE.h`, `EngineApp.h`,
ImGui, Optick). EditorLib's, UnitTests' and EditorHarness' PCHs are `UtilsPCH.h` alone: putting `RZE.h` and ImGui in
them as well saved only 3% more, and `Engine.h` changes in about one commit in eighteen, each time rebuilding every
EditorLib and UnitTests file.

Clean Debug build on Linux, compile time in total over all files (`clang -ftime-trace`):

| | Engine | EditorLib | UnitTests | All |
|---|---|---|---|---|
| Both PCHs named `StdAfx.h`, only Engine and Utils with one | 148 s | 95 s | 75 s | 379 s |
| Each named after its project | 90 s | 96 s | 71 s | 313 s |
| Layered on `UtilsPCH.h` | 64 s | 91 s | 71 s | 279 s |
| PCHs for EditorLib, UnitTests, EditorHarness | 63 s | 53 s | 44 s | 209 s |

On 32 cores the wall clock hardly changes (about 17 s), because the projects build one after another, each waiting
for the libraries before it to link. With fewer cores, such as CI's 4, the compile time is what the wall clock pays.

**The cost is in what an edit rebuilds.** A header in `UtilsPCH.h` rebuilds every project that has a PCH: touching
`Matrix4x4.h` rebuilds 293 objects in 12.1 s, against 132 objects in 8.6 s with no shared PCH. Editing the editor is
cheaper: a `.cpp` alone 1.7 s to 1.2 s, `EditorContext.h` (28 objects) 3.6 s to 2.8 s. So a header that changes
often doesn't belong in `UtilsPCH.h`.
